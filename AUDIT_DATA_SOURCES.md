# Аудит загрузчиков данных — MOEX Risk Dashboard MVP 0.9.3

Дата аудита: 12.08.2026.

## Итог

До исправления единая last-good логика была только у MR/LK и статических CSV. Контракты FORTS, OffDays и календарь специальных параметров при сетевой ошибке могли сразу перейти в ошибку/fallback без сохранения последнего успешного live-ответа. Ручной MR/LK принимался только как CSV, не сохранялся после перезапуска, а невалидная ручная загрузка могла заменить рабочий набор пустым DataFrame.

После исправления критичные источники работают по принципу:

**live официальный источник → последний успешный кеш → встроенный fallback, если допустим → сохранённый ручной файл.**

Явно выбранный пользователем upload валидируется первым как осознанная подмена. Если он не проходит проверку, приложение продолжает цепочку live/cache/fallback и не обнуляет данные.

## Проверка официальных источников

MOEX официально документирует методы `objects/limits` и `objects/staticparams`. В структуре `limits` указаны `ASSETCODE`, `MR1`, `MR2`, `MR3`, `LK1`, `LK2`, `TITLE`, `UPDATETIME`. На странице НКЦ «Риск-параметры» по-прежнему опубликованы ссылки на ставки рыночного риска/лимиты концентрации, статические параметры, календарь специальных риск-параметров и ширину коридора для торгов в выходные дни.

Среда сборки проекта не имела прямого DNS-доступа к `iss.moex.com`, поэтому независимый `requests/curl` из контейнера завершался DNS-ошибкой. Это не интерпретируется как отказ самого MOEX. Именно поэтому приложение теперь само показывает фактический runtime-статус каждого источника и не теряет last-good данные при сетевой недоступности.

## Формат и валидация MR/LK

Минимально обязательные колонки:

- `assetcode`
- `mr1`
- `mr2`
- `mr3`
- `lk1`
- `lk2`

Дополнительно поддерживаются:

- CSV с `;` и десятичной запятой;
- CSV со служебной строкой `limits` перед заголовком;
- XLSX с заголовком не обязательно в первой строке;
- строковые проценты вроде `13%` (нормализуются в `0.13`);
- `Код БА` как алиас `assetcode`.

Набор считается невалидным, если он пуст, отсутствует обязательная колонка или обязательная колонка целиком не содержит пригодных значений. До прохождения этой проверки last-good кеш не обновляется.

## Поведение при ошибках

1. HTTP error / timeout: выполняются короткие повторные попытки; затем используется last-good cache.
2. Пустой HTTP body: считается ошибкой, кеш не перезаписывается.
3. Неверная структура ответа: считается ошибкой, кеш не перезаписывается.
4. Повреждённый кеш: пробуется встроенный fallback, затем сохранённый manual.
5. Невалидный новый upload: upload отклоняется, существующая live/cache/fallback цепочка продолжает работать.
6. Валидный MR/LK upload: нормализуется и сохраняется в `runtime_cache/market_rates_manual.csv`.

## assetcode

Сопоставление сделано регистронезависимым и очищает обычные пробелы, NBSP и zero-width символы. В локальных наборах проекта проверено:

- static parameters: 192 уникальных кода;
- OffDays: 192 уникальных кода;
- evening registry: 192 уникальных кода;
- множества этих трёх источников совпадают полностью;
- календарь спецрежимов: 59 уникальных кодов, все входят в основной набор;
- регистронезависимых дублей в этих наборах нет.

## Что намеренно не подставляется

Для MR/LK встроенного «придуманного» fallback нет. Если live и last-good cache недоступны, используются только ранее подтверждённый ручной файл либо явный статус ошибки. Значения MR/LK не синтезируются.

`PREVSETTLEPRICE` в утреннем валютном блоке остаётся явно помеченным прокси для `Pmarket23:50`; это аналитическая оценка, а не официальный расчёт НКЦ.
