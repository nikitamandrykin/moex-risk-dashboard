# Проверка dashboard-v2

Production остаётся на main. Этот PR не включает его деплой или слияние.
Подтверждённого staging URL на момент изменения нет.

## Отдельный Railway staging

1. В отдельном окружении/сервисе подключить этот репозиторий и ветку dashboard-v2.
2. Использовать Dockerfile, MOEX_PUBLIC_DEPLOYMENT=1, target port 8501.
3. Создать отдельный домен сервиса. Не менять ветку и домен production.
4. Если Railway приостановил сборки, дождаться восстановления и успешного build.
5. Открыть staging-домен: проверить шесть карточек источников, даты наборов,
   резервные данные и диагностическую таблицу. Ответ API не означает свежую сделку.
6. Проверить поиск (в том числе пустую выдачу), фильтры, выбор строки и переход
   в карточку. После смены фильтра/снимка старый выбор строки должен сброситься.
7. Проверить все шесть разделов, ГО на LK1/LK2 и спецрежимы.
8. Оставить страницу открытой более 6 минут: снимок обновляется при включённом
   автообновлении. Повторить с выключенным автообновлением и ручным обновлением.
9. Проверить ширины 390, 768 и 1440 px; таблица допускает горизонтальную прокрутку.
10. Снять [MOEX PERF] для холодного запроса и время повторного поиска/переключения.

## Локально

Python 3.12, затем `pip install -r requirements.txt` и
`streamlit run streamlit_app.py`. Открыть http://localhost:8501.
Тесты: `python tests_dashboard_v2.py` и `python tests_dashboard_app.py`,
а также шесть существующих tests_*.py, перечисленных в CI.

## Измерение

На локальном синтетическом наборе 200 БА: первый расчёт с кэшем 0.4013 с,
повторный 0.0025 с. Это расчёт без сети, не ускорение загрузки Railway.
Проверяется равенство результата прямому расчёту и отсутствие повторного вызова
при неизменных входах. Кэш ограничен 32 наборами и TTL 60 с; календарные переходы
и московская дата участвуют в ключе. Сетевой TTL остаётся 300 с.
